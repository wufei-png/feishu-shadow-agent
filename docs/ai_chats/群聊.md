基于 `feishu-shadow-agent-flows.md` 和 MVP 主 spec，结合 Groklets、Vercel Slack Agent、CCCC、Xiajiao 等开源群聊 Agent 的常见模式，评估如下。

## 总体判断

**对 MVP 目标（owner 个人助手、群聊 `@我` 触发、低风险自动回复、其余走审批）来说，设计已经覆盖了群聊的主干路径，大约 70–80% 的常见场景。** 任务归属、活跃跟踪、closed recall、资源 gate、审批闭环、幂等发送这几块是成体系的，不是简单「搜消息 → 调 LLM → 回复」。

但如果按「生产级群聊 Agent」标准，仍有一些生命周期、可观测性和长期上下文边界需要明确，或标为 post-MVP。

---

## 已覆盖得较好的场景

| 场景 | 设计中的对应 |
|------|-------------|
| 首次 `@owner` 开新任务 | `group_at_me ingest` → `new_task` |
| 同 thread 续聊（不再 @） | `thread:<id>` shortcut + `active_watch.thread` |
| reply 续聊 | `reply_to msg` shortcut |
| 多人接力同一话题 | `watch_keys` + `user:<id>` |
| 任务超时后再问「上次怎么样了」 | closed task recall（7 天）+ `reopen_task` |
| 换题 / 多候选歧义 | TaskRouter + `ambiguous` → Approval |
| 群无 thread 的 follow-up | `active_watch.chat.<chat_id>` + watch_keys 过滤 |
| 图片/文件依赖 | bot gate + `234040` 降级通知 |
| 高风险/不确定回复 | reply policy gates + ApprovalRequest |
| `@All` 误触发 | `at_all` suppressed |
| 未知群处理但不自动回 | per-chat policy 默认 `auto_reply: false` |
| 发送可靠性 | dry-run + idempotency + 读回验证 |

和开源设计的对齐点：

- **Groklets / Orka**：mention 激活、per-channel policy、dedup、priority —— 你们用 `per-chat policy` + checkpoint overlap + message_id 去重，思路一致。
- **Vercel Slack Agent / Temporal 示例**：thread 级会话状态 —— 你们的 `Task Session` + `watch_until` + thread watch 是同类模型。
- **CCCC**：reply_to、审批、审计 —— ApprovalRequest + actions/logs 覆盖了核心部分。
- **双层路由**（确定性 shortcut + LLM Router）—— 和 pydantic-ai-temporal 的 dispatcher + specialist 一样，是控制成本和稳定性的常见做法。

## 尚未充分考虑或规则不够明确的场景

### 1. 同群多任务并发（无 thread 时）

主风险在 §3 消息归属，不在资源下载。同一 `chat_id` 无 `thread_id`、多个 active task 时：

- `active_watch.chat` 会合并拉取再分发，但**同一 sender 的两条消息可能分别属于不同任务**；
- 当前实现已按时间顺序处理同一 tick 的消息；同一 sender 的语义归属仍由候选和 Router 决定。

**剩余问题**：如果真实高流量场景仍出现错误 attach，应在 backlog 中增加可复现样本和指标，不再把处理顺序本身当作未实现项。

### 2. Agent/Bot 自身消息的回环

早期分析担心 `watch_keys` 命中 agent 消息会形成回环；当前代码已经记录 sender role 并在 ingress/processing 中执行 loop guard：

- owner 代发、bot 群回复和 readback 消息不会默认进入新 task 匹配；例外仍以代码中的明确 mention/reply 规则为准。
- 若线上出现新的回环样本，应补回归测试，而不是重新依赖 prompt 约束。

### 3. 消息生命周期事件

未覆盖：

- **撤回/编辑**：已处理消息被撤回，sent reply 悬空；
- **合并转发/跨群引用**：context 可能来自别的 chat，TaskRouter 易误判；
- **纯表情反应**（虽有 `reactions:read` scope）：有人只 react 不发言，是否算 follow-up？

MVP 可标为 ignore，但建议在 normalizer 层写清 `message_type` / `deleted` 的处理策略。

### 4. divided mention 场景

- `@owner` + `@其他人`：reply_target 默认 `reply_target_message.sender`，合理；
- **owner 在群里 @别人问问题**（@张三 你怎么看）：若 search 仍命中 `--is-at-me`，可能误开任务。

**建议**：normalizer 区分 `direct_mention` vs `incidental_mention`（owner 是消息作者且 mentions 不含「向 owner 提问」语义时 → suppress 或 ignore）。

### 5. 高流量群的成本与漏消息

`overlap_seconds: 120` + `tick_interval: 60` 对一般群够用。但：

- 历史风险是单 tick 受 `page_size` 上限影响，分页未完成就 sleep 可能**漏消息**；
- 无 thread 群用 `chat-messages-list` 拉 watch window，消息量大时**成本高、易超 tick**。

**代码复核**：当前 ingestion 已在分页 drain 完成、排序去重后推进 checkpoint；这条 P0 风险已由实现和回归测试覆盖。**仍待办**是高流量场景的 max_messages_per_tick、lag 指标和超时/积压恢复策略。

### 6. Hermes 会话与上下文策略的边界

MVP 明确不做 running summary / context budget，follow-up 只传增量。这在短对话里没问题，但群聊常见：

- 5–10 轮后 Hermes session 仍「活着」，但**早期关键信息只在 SQLite、不再注入**；
- session 丢失恢复时「按 id 补发历史」——**补多少、按什么顺序**未量化。

开源里（Slack Agent、Temporal 示例）普遍有 **thread summary 或滑动窗口 + 结构化 state**。你们用 `task_label` + `task_state` 部分替代，但复杂排障类话题可能不够。

**建议（post-MVP）**：`task_state` 里维护 `running_summary`（Hermes 每轮更新，约 200 字），不必重放全文。

### 7. 审批与并发

- pending approval、expired approval 和 task lifecycle 的边界已由后续 P6/P11 规则固定：expired 是历史状态，不关闭 task；读模型只派生 overdue，显式 maintenance/command 才推进状态。
- owner `/send` 与自动 pending approval 的发送竞态已由同一 task 与 reply target 的 active-send 约束、幂等键和 dispatch recovery 处理；仍应以 [MVP 幂等约束](../specs/feishu-shadow-agent-mvp-design.md#25-idempotency) 为准。

### 8. 身份与可见性

- bot 被踢出群：`bot_joined: true` 配置过时，下载/群回复失败后的**自动 policy 降级**未写；
- `auto_reply` 用 bot，但 bot 不在群 → fallback user；若群策略禁止 user 代发，行为未定义。

### 9. 产品向群聊场景（MVP 刻意不做，但要心里有数）

| 场景 | 现状 |
|------|------|
| 多人同时 @owner 不同问题 | 靠 TaskRouter，无优先级队列 |
| owner 委托「帮我转告 X」 | 无第三方 DM 工具权限 |
| 非文本消息（语音/视频/卡片） | 资源 gate 有，但无转写/卡片解析 |
| 跨时区/静默时段 | 无 schedule policy |
| 群成员 @bot（非 owner） | 入口是 `@owner`，不处理 |
| 飞书交互卡片审批 | 已实现但可选；远程、多用户形态仍是 post-MVP |

这些和 MVP 边界一致，不算设计缺陷，但属于「群聊 Agent 完整版图」里的空白。

## 合理性评估

**整体架构合理**，尤其适合「个人 shadow agent」而非「群里的公开 bot」：

1. **入口收窄**（只 `@me` + P2P）—— 正确，避免全群扫描和误触发。
2. **Python 状态机 + Hermes 无状态 Router** —— 成本与可控性平衡好；比「每条消息都问 LLM」稳。
3. **群自动回复默认关、per-chat 开** —— 比开源里 `mention` 即响应更保守，符合代 owner 发言的风险模型。
4. **user 读 + bot 下资源** —— 飞书权限现实下的正确拆法。
5. **Approval 统一抽象** —— 和 Groklets/Xiajiao 的 human-in-the-loop 一致，后续可接卡片 UI。

相对开源，**偏弱的三块**：

- **可观测性**：route audit 已有 match reason 和候选数量；仍缺每 chat/thread 的 lag、积压和高流量恢复指标；
- **耐久工作流**：daemon tick 够用，但 pending approval blocker 24h、跨天 recall 更适合 event-driven + durable workflow（Vercel WDK / Temporal 模式）；
- **delivery 语义**：CCCC 的 read cursor、reply-required obligation 你们用 `watch_until` 近似，但没有显式「这条消息是否已被 agent 消费」的对账。

对 MVP 来说不必上 Temporal；若 daemon 重启频繁，应保证 **task state + pending actions 从 SQLite 可恢复**，spec 已隐含，实现时需注意。

## 结论

当前设计**已经覆盖群聊 Agent 的主干**：触发、归属、跟踪、续聊、召回、资源、回复策略、审批、发送幂等。和开源方案比，**安全边界和飞书身份拆分**做得更细，这是优势。

主要缺口不在「少画了一个框」，而在：

- **消息生命周期与误触发边界**（撤回、编辑、reaction、跨群引用、incidental mention）；
- **高流量运维与成员状态自愈**（lag、积压、bot 离群）；
- **长跑对话的上下文**（刻意简化带来的长期话题漂移）；
- **确定性 shortcut 与多任务优先级**（closed recall、activation mode）。

若目标是「先跑通 1–3 个白名单群」，现有设计**足够合理**；若目标升级为「默认信任的多群生产助手」，应优先处理上述高流量可观测性、消息生命周期和长期上下文问题。
