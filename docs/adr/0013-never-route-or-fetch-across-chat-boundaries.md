# Never route or fetch across chat boundaries

Status: accepted

Reply targets, thread, sender, and mention shortcuts match tasks only within the message's own chat, and content that originates in another chat — typically carried in by a Merged Forward — is context text of the current chat only. A Cross-Chat Reference is never a routing signal, and the daemon never fetches origin-chat messages, state, or resources. This keeps task ownership, context, and operator visibility scoped to one chat, which is the safety boundary the owner relies on; enabling cross-chat matching was considered and rejected because it would require per-cross-chat authorization and visibility rules that do not exist today. Directly addressable child image/file markers inside a Merged Forward are downloaded only with the top-level container ID and never trigger origin-chat fetches. A 2026-09-21 runtime probe corrected an apparent file-acquisition failure: the visible `file_` key was a `<folder>` collection handle, so its direct request returned CLI `network/server_error` (HTTP `500`, upstream code `40009`, log ID retained only in redacted runtime evidence). Bot folder enumeration and downloads of two direct leaf files through the same container both succeeded. The runtime extracts direct leaf image/file markers, but deliberately excludes folder keys rather than recursively acquiring a collection without explicit limits and product policy. This is a local resource-safety boundary, not a routing change.
