# Never route or fetch across chat boundaries

Status: accepted

Reply targets, thread, sender, and mention shortcuts match tasks only within the message's own chat, and content that originates in another chat — typically carried in by a Merged Forward — is context text of the current chat only. A Cross-Chat Reference is never a routing signal, and the daemon never fetches origin-chat messages, state, or resources. This keeps task ownership, context, and operator visibility scoped to one chat, which is the safety boundary the owner relies on; enabling cross-chat matching was considered and rejected because it would require per-cross-chat authorization and visibility rules that do not exist today. Child resources inside a Merged Forward remain scoped to the current container and never trigger origin-chat fetches. A 2026-09-21 runtime probe established that a forwarded image can download through the top-level container ID, but a visible forwarded-file key returned network `500` twice and was omitted from the bot `mget --download-resources` resource list. The same result persisted after upgrading the runtime CLI from 1.0.56 to 1.0.96. The file therefore remains an undownloadable placeholder until the CLI/API exposes it through the container; this is an external acquisition dependency, not a routing change.
