# Ingest caps defer work through an un-advanced checkpoint; never truncate silently

Status: accepted

High-traffic acquisition is bounded per active chat/thread target (message/page cap), separately bounded per cross-chat search source, and bounded per tick by one shared wall-clock budget. A bounded Drain is never treated as success: when a source window is not fully fetched, `last_success_at` is not advanced. The checkpoint instead keeps the fixed `start`/`end`, the opaque next-page token, cumulative page/message counts, the defer reason, and restart count. A later tick resumes that exact window and only replaces it with a completed checkpoint after the terminal page has been processed.

Page tokens are treated as opaque and potentially expiring. A fetch failure on the first resumed page conservatively clears the saved token, records a restart, and fails that stage. The next tick restarts the same fixed window from its first page; message-id/revision upsert and routing audit idempotency make that replay safe. A newly returned token can then resume forward progress. Processing must complete before a resume token is saved, so a crash or routing failure can repeat work but cannot skip it.

The daemon rotates which of group search, P2P search, and active watch receives the first opportunity each tick. Active watch likewise rotates its ordered chat/thread targets. Approval inbox remains first because actual reply dispatch depends on its health; an incomplete approval-inbox drain blocks actual replies for that tick. Budget exhaustion never prevents later non-ingestion stages such as dispatch bookkeeping and retention from running.

Silently advancing the checkpoint past an undrained tail was considered and rejected because it would drop messages with no trace; the cost of recovering a lost message later is far higher than the cost of re-fetching bounded work. Persisting accumulated raw messages was also rejected: successfully processed pages already live in the normalized store, while retaining raw batches would expand sensitive durable state. Observable lag (checkpoint age, page/message counts, drain completion, backlog markers and budget exhaustion) is exposed through Operator Query slices, the local console, and JSONL logs, not only as daemon-internal state.
